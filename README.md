# AesculaMD Bootcamp

A stage-gated, competency-based pre-med curriculum for freshmen and sophomores — the "Roadmap → Agents → Community" product, prototyped here as a static, client-side mockup before any real backend work begins.

## What this is (and isn't) right now

This is a **front-end prototype**, not a production app. Everything runs in the browser with no server, no database, and no real AI — it exists to prove the interaction model (stage-gating, competency-tagged content, agent unlocking) before investing in real infrastructure.

**What actually works:** clicking through stages, marking a stage complete, seeing the next stage unlock, seeing the Agents and Know How pages update to match; a real interactive Stage 01 self-assessment (rate all 17 competencies, write reflections) that recomputes the roadmap order live; an Evidence Log page that aggregates every rating and stage reflection, grouped by competency — this is bootcamp's one real "tool," deliberately (see gap #25); a **Quick Setup** flow that reaches the same personalization without the guided lessons (see gap #7 below); a **Timeline** page with a runway-adequacy pace read; each **Stage Detail page** (a real page, not a modal — see gap #21) has an embedded, grounded AI advisor conversation with whichever agent owns that stage; a **PS Checker** page; a visible **source-citation panel** on every stage; a **"Should I Be a Doctor?"** reality-check quiz; a **fully responsive mobile layout**; a **My Profile** page aggregating Roadmap + Competency progress; a real-input, single-agent **Chat** (switch between all 8 agents, keyword-matched replies grounded in your real state, session history) — see gap #18; a real **Institutes pilot-application form** with an instant, honest fit read and a real countdown to the next enrollment deadline — see gap #19; live hosting on Vercel with continuous deployment from GitHub — see gap #24.

**What's simulated, not real:** there's no persistence (a page refresh resets everything), no real user accounts, no real AI agents (Chat's replies are scripted/keyword-matched against real state, not a model call — see gap #18), and no backend at all.

**What used to be here and was deliberately removed** (see gap #26): Activity Ledger, LOR Tracker, School List, Interview Simulator, and The Committee. Bootcamp and AesculaMD_1 are staying separate products — bootcamp is the free curriculum-and-AI-advisor front door, AesculaMD_1 is the full application-cycle platform students graduate into. These five were administrative/practice tools that duplicated more mature real versions already in AesculaMD_1, so they were cut rather than maintained twice.

## Running it locally

```bash
npm install
npm run dev
```

Opens a local dev server (Vite) with hot reload. `npm run build` produces a static `dist/` folder deployable anywhere (Vercel, Netlify, GitHub Pages, etc.) — there's no framework lock-in here, so this can also just be opened directly as a static site with zero build step if preferred.

## The single most important file: `src/data.js`

Every page (Bootcamp, Know How, Agents) renders from the same `STAGE_DATA` array. This was a deliberate choice: it means the stage sequence, competency tags, and agent-unlock logic can never silently drift out of sync between pages the way separately-hardcoded content would. If you add or reorder a stage, update it once in `data.js` — every page picks it up automatically.

Each stage object also has a `status` field (`done` / `current` / `locked`) that drives the gating logic in `app.js`. Right now this is just in-memory JS state; the real backend work is replacing that with actual per-user progress from a database.

## Content vs. code

The `/content` folder holds the full, real curriculum documents — multiple paragraphs per stage, full reflection framing, sourcing notes — that `data.js` condenses down to fit the UI. **`/content` is the canonical source; `data.js` is a lossy summary of it.** When you're editing actual curriculum language, edit `/content` first, then re-condense into `data.js` — don't edit the two independently or they'll drift.

Several stages in `/content` have a verification footnote at the bottom noting what's been fact-checked against AAMC/AACOM sources and what still needs review (Stage 08/Research in particular still needs a pass from a real advisor, not just search-verified facts).

## Known gaps / what "going deeper" actually means from here

This prototype deliberately does NOT solve, and the next phase of real work should prioritize:

1. **Auth + a real database** — user accounts, and `STAGE_DATA.status` (and `evidenceLog`, `selfAssessment`) becoming real per-user progress instead of shared, refresh-resets-everything in-memory state. Nothing below this line matters to a real student until this exists.
2. ~~The self-assessment mechanism from Stage 01~~ — **built.** All 17 competencies are ratable (Planning/Progressing/Demonstrating) with per-competency reflections, live in `app.js`'s `renderAssessment`/`setAssessmentLevel`/`updateReflection`. Simplification worth knowing: content describes three distinct reflection prompts per rated competency; the built version collects one free-text reflection instead.
3. ~~Real AI agents~~ — **Chat is now scripted, not a real model** (see gap #18): keyword-matched, state-grounded replies, not a static one-bubble mock anymore, but still not a real conversation. Real agents need the AMCAS own-words constraint (no drafting submittable essay/activity text) built in as an actual behavioral guardrail, not just a content warning — see `content/stage-01-premed-101.md` for the framing. That constraint is already respected in Narrative Thread's scripted replies (it explicitly declines to draft), but a real model would need it enforced in code, not just in a reply template.
4. ~~The evidence log~~ — **partially built.** Every Stage 01 rating and every stage's reflection prompts (all 10 stages, auto-tagged to that stage's target competencies) now feed a live `evidenceLog` array, browsable by competency on the new Evidence Log page (`app.js`'s `renderEvidenceLog`). Still missing from `evidence-log-design.md`'s full design: append-only history (this prototype overwrites an entry in place when re-edited, rather than superseding it with a new dated one), the lock-on-submission behavior, agent-suggested tags, and the opt-in aggregate-research flywheel — all of those need the backend from gap #1 first.
5. ~~Roadmap personalization logic~~ — **built.** `computeRoadmapOrder` in `app.js` implements all three terms from `roadmap-generation-design.md` §2: `gap_weight` (stages get pulled earlier when their target competencies are rated low), `urgency_weight` (Stage 05 has a real `<input type="month">` testing-window field — a date within 6 months pulls Grades & MCAT forward), and `track_weight` (Stage 04's MD/DO/dual choice is a real selector — choosing DO or Dual pulls Clinical Experience and Personal Brand forward). Recomputes on Stage 01 update, Strategy completion, and Grades & MCAT completion. Known limitation, stated in the spec: `gap_weight` can't act on **Resilience and Adaptability**, since no stage's `competencies` field owns it by design — see `roadmap-generation-design.md` §2 for why.
6. ~~The Cost & Access stage placement~~ — **resolved.** Cost & Access is now Stage 03 (right after Narrative, right before Strategy), not last — see `content/roadmap-generation-design.md` §3 for the reasoning. Strategy is now 04, Grades & MCAT 05, Clinical Experience 06, Volunteering 07, Research 08, Leadership 09, Personal Brand 10; `data.js` and every `/content` cross-reference were updated to match.
7. ~~No way to skip the guided lessons, and no calendar-based roadmap~~ — **built.** See `content/roadmap-timeline-design.md`. **Quick Setup** (Home page → "Quick Setup") collects the same self-assessment, MD/DO/dual track, and testing-window inputs as the guided flow, plus two new ones — current year in school and target application-cycle year — then sets `skipModeActive = true`, which stops `locked` from blocking completion anywhere in the app (`app.js`'s `handleStageCta`). The **Timeline** nav page (`computeTimeline`/`renderTimeline`) turns `roadmapOrder` into an actual term-by-term (Spring/Summer/Fall) plan from now through the target cycle's primary-submission window, with the MCAT date, AMCAS primary submission, secondaries, and interviews overlaid as real milestones. Stated limitation, not a bug: scheduling is a greedy even distribution across terms, not a deadline-aware constraint solver.
